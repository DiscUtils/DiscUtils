# NTFS journal recovery and Windows hibernation

## What a volume stream can show

Windows writes the resume image to `hiberfil.sys` on the Windows volume. Full hibernation saves the system and user sessions. Fast Startup logs off users and saves the kernel session and drivers. A reduced hibernation file supports Fast Startup. Windows documents distinguishing the two resume modes through power transition information supplied to drivers. This information is unavailable to a reader of one NTFS volume. The guard makes the same decision for either kind of local resume image. [Microsoft system power states](https://learn.microsoft.com/en-us/windows/win32/power/system-power-states) · [Fast Startup and resume](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/distinguishing-fast-startup-from-wake-from-hibernation)

| Local observation | Recovery decision | Evidence |
| --- | --- | --- |
| The first four bytes of a readable header are `hibr` or `HIBR` | Positive local evidence of a saved resume image. Refuse. | NTFS-3G checks both spellings. Windows hibernation file studies describe these signatures in the `PO_MEMORY_IMAGE` header. [NTFS-3G hiberfile check](https://github.com/tuxera/ntfs-3g/blob/7f0f841fc52cf719106c5c93bafe465004e36816/libntfs-3g/volume.c#L786-L850) · [Sylve et al., 2016](https://doi.org/10.1016/j.diin.2016.12.003) |
| The header starts with `HORM` | Positive local evidence. Refuse. | The format study identifies the signature. Microsoft documents Hibernate Once/Resume Many reusing the saved resume image. [Format study](https://www.cct.lsu.edu/~golden/Papers/sylvehiber.pdf) · [Microsoft HORM documentation](https://learn.microsoft.com/en-us/windows/configuration/unified-write-filter/hibernate-once-resume-many-horm) |
| The 4 KiB header is physically readable and zeroed, or starts with `wake` or `WAKE` | No local evidence of an active resume image. | The libhibr format notes describe `wake` and `WAKE` as invalidated resume images. A Windows 8–10 study observed `WAKE` after resume and found it could persist through full shutdown. In the project maintainer's forensic experience across Windows versions, Windows can retain `hiberfil.sys` after resume while clearing its former contents with TRIM, leaving the first 4 KiB entirely zero. Such zeros indicate no local saved resume image, not that the volume is necessarily safe to modify. [Windows measurements](https://www.cct.lsu.edu/~golden/Papers/sylvehiber.pdf) · [libhibr format notes](https://github.com/libyal/libhibr/blob/main/documentation/Windows%20Hibernation%20File%20%28hiberfil.sys%29%20format.asciidoc#212-signature) |
| `RSTR` or `rstr`, other nonzero header bytes, a file shorter than 4 KiB, or a failed lookup or read | Indeterminate. Refuse. | The format study identifies `RSTR` as a transition during resume. NTFS-3G refuses short files and read errors. Its short-file diagnostic refers to a non-system partition. DiscUtils treats a short file as ambiguous because truncation can produce the same result. [Format study](https://www.cct.lsu.edu/~golden/Papers/sylvehiber.pdf) · [NTFS-3G hiberfile check](https://github.com/tuxera/ntfs-3g/blob/7f0f841fc52cf719106c5c93bafe465004e36816/libntfs-3g/volume.c#L796-L850) |
| A readable root index contains no `hiberfil.sys` | No local evidence. Ordinary NTFS data volumes remain eligible for recovery. | The resume image lives on the Windows volume. An NTFS data volume can lack a local file whether or not Windows still has state for that volume. [Microsoft system power states](https://learn.microsoft.com/en-us/windows/win32/power/system-power-states) · [NTFS-3G mount guidance](https://github.com/tuxera/ntfs-3g/blob/7f0f841fc52cf719106c5c93bafe465004e36816/src/ntfs-3g.8.in) |

NTFS-3G 2026.9.28 checks the root file before read-write mount. It also separately refuses LFS 2.0 because Windows may have cached metadata, and the implementation explicitly observes that an ordinary abrupt termination can leave the same version. The five DiscUtils Windows crash images use LFS 2.0. The version remains a format selector in DiscUtils. The volume dirty bit can indicate outstanding writes or corruption. The boot geometry and journal restart state describe the volume and its log. None of these fields establishes Windows' power state. [NTFS-3G mount checks](https://github.com/tuxera/ntfs-3g/blob/7f0f841fc52cf719106c5c93bafe465004e36816/libntfs-3g/volume.c#L678-L729) · [Microsoft dirty-bit documentation](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/fsutil-dirty) · [Windows crash-image tests](../Tests/LibraryTests/Ntfs/Journal/NtfsJournalWindowsSampleTest.cs)

The project maintainer has also observed the documented header signatures consistently in forensic applications on recent Windows versions. This practical experience supports the signature classification without requiring fresh Windows 11 captures as a merge prerequisite. It does not establish universal ownership safety or prove support for every possible file layout. Unknown nonzero headers and unreadable mappings remain indeterminate and prevent recovery.

Linux NTFS3 has a separate read-only replay path and tracks whether the journal still needs replay. Its dirty-volume remount check and `force` option provide no basis for treating a stream as free of saved Windows state. The older Linux `ntfs` implementation is a separate driver. Its local check recognizes a completely zeroed 4 KiB header and treats unfamiliar nonzero data conservatively. [Linux NTFS3 replay](https://code.googlesource.com/linux/torvalds/linux/+/4bf54e47525dcacd4c6cdd97fb5902592414dd7a/fs/ntfs3/fslog.c#4844) · [NTFS3 remount policy](https://github.com/torvalds/linux/blob/master/fs/ntfs3/super.c) · [Linux ntfs local check](https://code.googlesource.com/linux/torvalds/linux/+/68ff4a3ccda9f98c74f23c70c8c7c581f9eee931/fs/ntfs/super.c#1054)

## Recovery admission

The probe reads only the supplied NTFS volume stream. It uses the root `$I30` lookup with `$UpCase`, follows the matching file reference, and reads the first 4 KiB of the unnamed `$DATA` from the mapped clusters. The prefix must be initialized and physically mapped in the first attribute extent. Synthesized sparse or uninitialized zeros, special layouts, ambiguous references and lookup or read failures prevent admission. A recognized signature is a reason to refuse or a marker of local invalidation. The probe does not validate the version-specific memory image or its checksum.

The guard runs for otherwise admissible journal recovery, including reset when there are no changed metadata pages. It checks both the original volume and, when there are staged changes, a private read-only view of the proposed result. The original view preserves evidence that redo could remove. The staged view can expose a file or header that redo would make visible. If a planned repair can replace a torn `$MFT` bootstrap record, the original lookup can bootstrap from the validated `$MFTMirr` location. The staged view must have a readable primary. The guard completes before any metadata, mirror or restart-page write and introduces no backing-stream flushes.

| Entry point or mode | Behavior when the guard refuses |
| --- | --- |
| `NtfsJournal.Analyze` | Returns `Unsupported` with the reason and leaves the backing stream untouched. |
| `NtfsJournal.Replay` and writable `Replay` construction, including the factory | Throws `IOException` before writing. |
| Read-only `Replay`, including the read-only default | Reports `Unsupported` and omits the overlay. The original view is available if its metadata can be read. A replayed view cannot account for Windows' suspended memory state. |
| `Refuse`, including the writable default | Applies the existing refusal for an unsupported journal. |
| `Ignore` | Bypasses journal handling and the local probe. It never initiates journal recovery. |

An empty or clean journal is a no-op and does not run the hibernation probe. `Clean`, `NoLocalEvidence` and `CanReplayPersistently` cannot establish exclusive ownership. A data volume may still be owned by Windows when the resume image is elsewhere. Callers must supply an offline volume with exclusive access and establish that no suspended or running operating system owns it. The guard cannot reconstruct missing evidence, attest the entire directory tree or detect an out-of-band change during recovery.

## Windows qualification

The added tests use synthetic headers, metadata damage, read faults and staged replay. They exercise the stream and admission paths. The five unchanged Windows crash images qualify the existing recovery comparisons on captured data volumes. They were produced by abrupt VM power-off and do not qualify hibernation detection. Published measurements, libhibr's format notes and the maintainer's continuing forensic observations support the header distinctions. Current Windows 11 captures would provide additional independent qualification of the file layout and the observed states, but are not a merge prerequisite. [Existing Windows capture procedure](ntfs-journal-recovery-qualification.md)

1. Use a disposable Windows 11 VM with an NTFS Windows volume and a second disposable NTFS virtual disk. Use a hypervisor configuration where the guest reports the relevant options through `powercfg /a`. Record the Windows build, firmware, virtual disk format and sector sizes. Keep the second volume mounted in the guest. Use guest power transitions and keep the host's volumes outside the test.
2. Start each run from a clone of the same clean guest. Enable hibernation in the guest with `powercfg /hibernate on` and run each transition below separately. Repeat the full-shutdown case after a verified successful resume to capture a possible consumed header. A VM save-state or a rejected power command does not qualify the run. [Microsoft shutdown command reference](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/shutdown/)

   | Capture | Guest command |
   | --- | --- |
   | Full hibernation | `powercfg /h /type full`, then `shutdown.exe /h` |
   | Fast Startup | `shutdown.exe /s /hybrid /t 0` with Fast Startup available |
   | Full shutdown with hibernation enabled | `shutdown.exe /s /t 0` |

3. After the guest powers off, copy both virtual disks before booting or mounting them. Hash the copies. Use a read-only image reader to expose each NTFS partition stream. Record the root entry, its unnamed data allocation and initialized lengths, the first 4 KiB signature, the `$Volume` flags and the journal version and state. Corroborate the header and allocation with an independent read-only reader. Keep the saved memory contents private.
4. In a local `LibraryTests` case, run `NtfsHibernation.Probe(volume, JournalVolumeLayout.Read(volume))` on each captured partition and record `NtfsJournal.Analyze(volume)`. Verify positive local evidence for a confirmed active system capture and verify the observed classification of the inactive capture. Record what is visible on the secondary disk independently of the primary. A missing local marker on the secondary disk is expected to be inconclusive.
5. Exercise persistent replay on a separate disposable copy only if the journal needs recovery. Check that refusal leaves the complete image hash identical. If the active Windows captures all have clean journals, use a separate synthetic recoverable journal on a derivative copy to exercise admission. Keep the native header observation and synthetic admission result distinct.

As an optional follow-up, obtain current Windows evidence for full hibernation, Fast Startup and a full shutdown with hibernation enabled. Record any unexpected header, uninitialized prefix or layout refusal before deciding whether the policy needs to change. These synthetic tests and published observations do not constitute native Windows 11 file-layout qualification. The secondary-volume limitation remains even if the captures pass.
