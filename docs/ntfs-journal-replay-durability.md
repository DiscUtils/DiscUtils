# NTFS persistent replay and storage durability

`NtfsJournal.Replay` and explicit persistent replay on filesystem open use the same write path. Replay is not atomic. An interrupted call can leave partially updated metadata, and an exception can occur after bytes become visible or reach storage. Use an offline volume with exclusive access. The caller must establish the guarantees of the supplied stream and its backing storage. `Replayed` reports writes, a journal reset and successful returns from the flush calls on that stream.

## Write sequence

| Phase | Ordering dependency | Retry after an interruption |
| --- | --- | --- |
| Analyze and prepare | Validate admission, stage the metadata, and prepare the required restart pages before writing. The existing undo, client-slot, mapping and hibernation checks apply. | An unsupported state leaves the volume unchanged. |
| Write and flush `$MFTMirr` if needed | The corresponding primary MFT record can advance its page LSN only after the mirror barrier. | An unchanged primary can still be redone after a partial mirror write or a failed mirror flush. |
| Write and flush primary metadata | Every metadata update must pass the barrier before publishing a clean restart page. Flush even when there are no new metadata writes to drain any bytes left buffered by a previous attempt. | A valid protected page can skip an already-applied operation using its LSN. A torn page must have a complete supported replacement or replay refuses it. Supported raw updates can be applied again in log order. |
| Write and flush the alternate restart page | Keep the dirty source available until the alternate reset passes the barrier. | A torn alternate can be discarded if the dirty source remains valid. If the two pages form a recognized partial reset, replay rechecks the log end LSN and requires no pending metadata changes or undo. The preceding unconditional flush also covers a visible but buffered alternate on a retry through the same stream. |
| Write and flush the dirty source restart page | The alternate has already passed its barrier. | A torn source can leave one valid clean restart page and reduced redundancy. A failed final flush can leave two clean pages visible on the live stream. That retry is a clean no-op, while reopening from storage may still find a partial reset. |

The order is the same for either source restart-page offset. Once a write or flush throws, replay issues no later writes. A backend can still retain part or all of the failed operation, or propagate buffered writes after the call returns.

The first four MFT records are mirrored on ordinary layouts. The Windows `s64k` fixture has a 64 KiB `$MFTMirr` with matching reserved records beyond the fourth record and differing bytes later in the cluster. Replay copies complete declared records in the reserved range that fits in the mirror and leaves the remaining bytes as stored. Microsoft's NTFS developer notes reserve the first 16 records for special files. NTFS-3G sizes the mirror from the cluster geometry and limits its match check to 16 records based on observed Windows behavior. This evidence establishes a supported prefix for replay. It leaves the mirroring policy of later records across Windows versions unqualified. [Microsoft MFT notes](https://learn.microsoft.com/en-us/windows/win32/devnotes/master-file-table), [NTFS-3G mirror geometry](https://github.com/tuxera/ntfs-3g/blob/edge/libntfs-3g/bootsect.c), [NTFS-3G match check](https://github.com/tuxera/ntfs-3g/blob/edge/libntfs-3g/volume.c)

## What a flush establishes

A successful `Write` means the stream accepted the bytes. A subsequent read can see those bytes while they still reside in a managed buffer, an overlay or an OS cache. A wrapper can forward its pending data and flush to the next layer. An OS file synchronization call requests a further boundary. Power-loss survival depends on the filesystem, storage server or hypervisor, controller, media and their cache and write behavior.

| Supplied stream or configuration | Flush behavior in replay | Established behavior and remaining limits |
| --- | --- | --- |
| Direct `FileStream` | A non-owning `SparseStream.FromStream` adapter requests `Flush(true)` | Requests OS file synchronization. The runtime, filesystem and storage must honor the request and report errors. This call does not establish sector atomicity or protection from every device failure. |
| Partition ranges and fixed VHD content | `SubStream.Flush(true)` forwards to its parent, including nested sparse wrappers | A backing `FileStream` receives `Flush(true)`; custom sparse wrappers can implement their own virtual `Flush(bool)` contract. |
| `SparseStream.FromStream`, synchronization, cache and other forwarding wrappers | Their `Flush(bool)` implementations forward the request through the wrapped stream | A wrapped `FileStream` receives `Flush(true)` and a wrapped `SparseStream` receives its virtual overload. Unknown `Stream` implementations receive `Flush()`. |
| Dynamic or differencing VHD content | Writable `DynamicStream.Flush(true)` forwards to its image file stream | Requests a backing disk flush when supported, after payload and current allocation writes have been issued. Deferred footers and container allocation crash behavior require separate qualification. |
| Writable VHDX content | `ContentStream.Flush(true)` forwards through its sparse image backing stream | This reaches the backing stream on the writable path, subject to any further wrapping. NTFS replay gains no guarantee about container-level crash recovery from that call alone. |
| Memory, a live snapshot, or a custom seekable stream | Virtual `SparseStream.Flush(bool)` defaults to `Flush()` if not overridden | A `MemoryStream` provides visibility in memory. An active `SnapshotStream` keeps overlay writes separate even when it flushes its base. Other implementations require an independently established contract. |

`NtfsJournal.Replay` continues to accept `Stream`; it creates a non-owning `SparseStream` adapter for the flush boundaries only. There is no journal-specific inspection of a nested `FileStream`. An implementation that overrides the parameterless `Flush()` but also derives from a built-in forwarding wrapper should override `Flush(bool)` if it must intercept the stronger request.

Modern `FileStream.Flush()` dispatches with `flushToDisk: false`. On Windows the disk-flush path uses `FlushFileBuffers`, including on Microsoft .NET Framework. On Unix, modern .NET requests file synchronization using the runtime's native implementation. Linux `fsync` waits for the device's reported completion. macOS distinguishes `fsync` from `F_FULLFSYNC`, which requests that the device flush its cache. The exact Unix primitive and error handling depend on the runtime version and platform. A .NET Standard build inherits the behavior of its host runtime. The .NET Framework-targeted tests run on Mono locally and check API dispatch, with native Windows coverage from CI. [FileStream API](https://learn.microsoft.com/en-us/dotnet/api/system.io.filestream.flush), [modern FileStream source](https://source.dot.net/System.Private.CoreLib/src/runtime/src/libraries/System.Private.CoreLib/src/System/IO/FileStream.cs.html), [.NET Framework source](https://github.com/microsoft/referencesource/blob/main/mscorlib/system/io/filestream.cs), [OS synchronization APIs](https://learn.microsoft.com/en-us/dotnet/api/system.io.randomaccess.flushtodisk), [Linux fsync](https://man7.org/linux/man-pages/man2/fsync.2.html), [Apple fsync](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html)

There is also a runtime error-reporting limitation. With .NET 10.0.0 on Linux, a probe against a disposable file observed `fsync` for `Flush(true)` and no `fsync` for `Flush()`. A replay probe on a copy of the `s4kn` fixture behind two built-in `SubStream` ranges reached `fsync` at all three reset boundaries. Injecting `EIO` into those calls still let replay return `Replayed = true`. This reproduces the upstream Unix `SystemNative_FSync` issue and tests error reporting. Qualify the deployed runtime and filesystem when relying on error propagation. [Runtime issue and syscall-injection reproduction](https://github.com/dotnet/runtime/issues/135201), [upstream correction](https://github.com/dotnet/runtime/pull/124725)

## Evidence and remaining work

The interruption tests track a live byte image separately from a simulated stable image. They check the issued operations and exact stable bytes at each boundary, including partial writes, a flush that throws before or after advancing the stable image, and reopening after the final successful flush. They cover same-stream retry, retry from the simulated stable image, and repeat recovery on a clean journal. Separate tests verify disk-flush dispatch for file and partition streams, propagation through sparse wrappers and dynamic VHD content, and fallback to parameterless flush for unknown streams. The five Windows crash-image comparisons exercise NTFS replay results. The extra large-cluster mirror update is synthetic and uses the geometry of one of those images.

The model can also acknowledge a flush while discarding one metadata write. A recognizable partial reset with missing metadata is refused without further mutation. If both clean pages survive while that update is lost, reopening reports a clean journal and cannot diagnose the lost update. The tests establish these behaviors for controlled writes and barriers. Actual power loss can also damage previously flushed data or both restart pages, or interrupt a container allocation update. Those cases require qualification on the deployed storage stack.

Keep the stream API and existing admission policy for this change. Before relying on power-loss durability for wrapped or remote storage, qualify the runtime, image container, filesystem and device using disposable images. The new overload requests a stronger flush where available but is not an end-to-end guarantee: custom wrappers and external storage layers must implement and honor the request. If an explicit contract is needed, a replay-specific option can accept a caller-provided barrier that covers the whole storage stack after each stream flush, propagates failure, and is invoked before any dependent write.
