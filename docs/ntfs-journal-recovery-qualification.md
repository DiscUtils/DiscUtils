# NTFS journal undo and interrupted replay

## What the evidence covers

The Windows crash images from PR #87 compare DiscUtils recovery with Windows on the same captured volumes. The PR reports 13 comparisons and 25 hard power-offs, none of which produced an unfinished transaction whose undo changed metadata. The five images in the test suite remain useful for redo and mount comparisons. They do not qualify metadata-changing undo. [PR #87 and its validation procedure](https://github.com/LTRData/DiscUtils/pull/87)

Windows Internals describes checkpoint analysis, forward redo and rollback of uncommitted transactions through backward links. It also describes logging recovery's undo operations so Windows can repeat them after another interruption. That account establishes the need for restartable undo. It does not establish the current on-disk compensation format, prepared transaction outcomes, ordering for overlapping transactions or a replacement for a compensation LSN. [Windows Internals, NTFS Recovery Support](https://flylib.com/books/en/4.491.1.110/1/)

DiscUtils builds the transaction table from checkpoint entries and later records. A commit resolves the transaction, a forget removes its slot, and a logged compensation or end of a top-level action can advance the undo cursor. An unresolved prepare is refused. For active transactions the in-memory replay follows each validated backward chain. It refuses cross-client or cross-transaction pointers, links outside the transaction's retained history, missing or remapped undo targets, and pending rollback in two transactions that touch the same physical cluster. Bitmap bit runs are the exception: two transactions may roll back different bits of one cluster, because setting or clearing disjoint bits gives the same result in any order. They are refused only when their bits overlap. Those are limits of the implementation. They do not define what Windows can recover.

The former `LastLsn + 1` marker had no corresponding log record. It also made the second inverse on the same cached page skip its work. In-memory undo now keeps the page's historical LSN and applies the chain without using a page stamp as an undo cursor. A page LSN outside the usable history for an inverse operation causes refusal. `CanReplayPersistently` is false when the journal needs metadata undo, including when the net overlay has no changes. Explicit persistent replay refuses before writes or journal reset. An inverse already recorded in the journal can still be redone as a logged action.

## What the interruption tests model

Tests use a live byte view and a separate persisted image. A completed barrier transfers pending writes into the persisted image. A cut can discard pending writes or retain the specified prefix of the failing write. Each retry starts from the persisted image. The tests exercise mirror and primary writes, metadata barriers, both restart-page writes, and a second cut during retry. A simulated torn primary that lacks a usable replacement is refused. A complete replacement can be redone even if the torn header already contains its LSN.

Replay stages all writes, flushes mirror changes before the primary MFT, and flushes metadata before resetting either restart page. It publishes and flushes the alternate restart page before overwriting the dirty source. A recognizable clean reset paired with its dirty source is completed only if reanalysis agrees with the reset LSN and finds no pending metadata changes or undo. A torn second write can leave a single valid clean restart page and reduced redundancy. Equal-LSN copies that conflict about the need for recovery or the active checkpoint are refused unless they form a matching reset pair.

This model does not establish crash atomicity. A real backend must honor the barriers and the tested sector-write assumptions. Recovery cannot detect every inconsistent image produced by a backend that persisted a clean reset ahead of metadata. See [persistent replay and storage durability](ntfs-journal-replay-durability.md) for the flush behavior of supported stream configurations.

## Bounded Windows VM qualification

1. Use a disposable Windows VM and a second reference VM or a clean snapshot of the same build. Attach a newly created, fixed-size VHDX as a secondary data disk. Record the VM identity, Windows build, disk identity, sector and cluster sizes, and workload source and seed. Restrict formatting, workloads and crash attempts to the verified disposable data disk and test VM. Keep the host volume and guest system disk out of the experiment.
2. Save a powered-off baseline copy of the initialized data VHDX. Use a repeatable metadata-heavy workload on that disk, such as concurrent directory renames, index growth, file deletion and sparse allocation. Start from the baseline for each attempt. Bound the initial campaign to 30 hard power-offs or two hours, whichever comes first. Power off only the identified test VM. With it stopped, copy and hash the data VHDX before Windows can mount it again. A guest debugger can narrow the cut window in a follow-up when a recovery boundary is verified for the exact Windows build.
3. Inspect each capture offline using a read-only parser or manual log decoding independent of DiscUtils. Retain a candidate only if it has a valid checkpoint, an active transaction with a reachable metadata undo operation, and evidence that Windows must change metadata to roll it back. An absent commit alone is insufficient. Preserve the original capture, both restart pages, relevant log records and the target metadata before recovery. Exclude candidates produced by editing the captured journal or by an orderly dismount.
4. Give Windows and DiscUtils separate copies of the qualifying capture. Let Windows recover on first mount in the reference VM with no workload. Save the recovered image before running any repair. Capture filesystem consistency diagnostics separately. Compare the DiscUtils in-memory result against the Windows image at the metadata level, including the affected MFT records, index entries, allocation bits and file references. Record differing LSNs, update sequence values and mount-generated metadata explicitly. Use the log and the before and after images to distinguish a rollback from ordinary redo. Compare at least two independent Windows recoveries of the same capture before making it a fixture.
5. Preserve hashes, workload timing, log evidence, affected ranges and the Windows comparison result with any accepted fixture. Seek at least one confirmed file-record or index undo and one confirmed allocation-bitmap undo before drawing broader conclusions. If the attempt budget expires without a qualifying capture, record that outcome and keep persistent metadata undo disabled. A later campaign for persistent undo would also need independently observed compensation records, Windows remount behavior after interruption and backend-specific durability tests.
